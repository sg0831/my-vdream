## 1. 개발 원칙

1. **PR 머지가 곧 배포.** 1일차에 CI, 3일차에 CD를 붙이고 그 뒤로는 사람이 서버에 들어가지 않는다. 마지막 날 배포 문제로 밤새지 않는다.
2. **팀처럼 작업한다.** 혼자여도 `main`에 직접 커밋하지 않는다. 이슈 → 브랜치 → PR → CI → squash merge. 채용 공고가 CI/CD와 브랜치 활용을 본다고 했으므로 커밋 히스토리와 PR 목록이 포트폴리오의 일부다.
3. **보는 사람의 1분을 설계한다.** 랜딩 → 역할 버튼 → 첫 화면에 데이터가 가득 → 버튼 한두 개 눌러보기. 이 경로에 있는 화면을 먼저 완성한다.
4. **세로 슬라이스.** 도메인 하나를 API, 관리자 화면, 모바일 화면까지 하루 안에 끝낸다. 절반만 된 기능 열 개보다 끝까지 된 기능 다섯 개.
5. **시드 데이터가 곧 데모다.** 기능을 만들 때마다 시드에 그 기능의 데이터를 넣는다. 마지막에 몰아서 만들지 않는다.
6. **접근성은 컴포넌트에서.** 큰 버튼, 상태 뱃지, 목록 항목 컴포넌트에 레이블과 포커스를 넣어 두고 화면은 그 컴포넌트만 조합한다.
7. **문서는 README 하나.** 설계 문서는 이미 있다. 개발 중에는 README만 갱신하고 설계 문서는 바뀐 결정이 있을 때만 고친다.

## 7. 완료 정의 (제출 기준)

1. 이력서 링크를 열면 HTTPS 랜딩 페이지가 뜨고, 네 역할 버튼으로 각 화면에 들어가며, 모든 첫 화면에 시드 데이터가 보인다.
2. 데스크톱에서 근로자 화면이 휴대폰 프레임 안에 보이고, 실제 휴대폰에서는 전체 화면으로 보인다.
3. 공고 작성 → 승인 → 지원 → 심사 → 면접 → 합격 → 출근일 → 재직 흐름이 운영 환경에서 동작한다.
4. 근로자가 출근 → 업무 시작·완료 → 업무일지 작성·제출 → 퇴근을 하고, 기업 담당자가 업무일지를 확인하거나 보완 요청한다.
5. SA 버튼으로 데모 데이터가 시드 상태로 초기화된다.
6. 근로자와 기업 담당자의 쪽지 대상 목록에 자기 기업 담당 매니저만 보이고, 규칙 밖 수신자로 보낸 API 요청은 403이다. 매니저는 모든 사용자에게 보낼 수 있다.
7. 기업 담당자가 3개월 기간의 월간 장애인 고용 리포트를 화면과 엑셀로 받고, 판정 네 종류(2배수, 1배수, 제외 가능, 확인 필요)와 데이터 경고가 시드에서 보인다.
8. Lighthouse 접근성 90 이상, 스크린리더로 핵심 흐름 통과.
9. GitHub 저장소에 `main` 보호 규칙, 30개 이상의 머지된 PR, CI와 Deploy 워크플로 실행 기록, Deployments 이력, `v1.0.0` Release가 있다. `main`에 직접 push한 커밋이 없다.
10. README에 데모 링크, 계정, 아키텍처, 스크린샷, 실행 방법, 브랜치 전략과 CI/CD 그림, 확장 계획이 있고 CI·Deploy 배지가 녹색이다.
